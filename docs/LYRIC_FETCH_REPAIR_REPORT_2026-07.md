## 4. 本轮新增修复细节

### 4.1 QQ QRC 行间元数据

此前转换器以相邻两个 QRC 行时间戳作为切片边界，只移除 `(start,duration)` 逐词标记。如果 `[kana:]` 等标签出现在两个时间行之间，它会落入前一行的正文切片。

现在转换器会在每个正文切片内移除形如 `[name:value]` 的元数据标签，再移除逐词标记并生成 LRC。这个规则只作用于已进入时间行正文的标签，不改变头部元数据的保留白名单。

新增用例覆盖：

- `[kana:]` 位于两个时间行之间时不会污染上一句；
- XML `LyricContent` 属性通过字符引用包含换行时仍能拆成两条歌词；
- 原有合法行时间戳与损坏时间戳兜底行为保持不变。

### 4.2 网易无歌词响应

网易响应可能通过顶层 `nolyric` 或 `uncollected` 表示纯音乐或歌词未收录。此前解析器只读取 `lrc/tlyric/yrc/ytlrc`，因而可能把“纯音乐，请欣赏”一类占位文本保存成歌词。

现在 `ExtractLyricTexts` 在读取任何歌词字段前检查这两个标志。只有 JSON 布尔 `true` 会触发空结果；字符串、数字或仅凭文案不会触发，以免误删真实内容。

新增用例覆盖：

- `nolyric: true` 同时带 LRC、翻译和 YRC 占位内容；
- `uncollected: true` 同时带看似有效的 LRC；
- `nolyric: "true"` 不被当作正式布尔标志；
- provider 完整搜索路径把无歌词响应过滤为 0 条歌词结果。

## 5. 未修复或需要后续讨论

### 5.1 网易加密接口备用方案（F2）

当前明文 v1 端点实现简单且仍可用，不建议在没有故障证据时直接替换。建议在出现以下信号后启动 eapi 迁移：

- 多地区、持续性的 4xx 或空响应；
- 同一网络下搜索接口正常而歌词接口持续受限；
- 修改请求头、Cookie 或短退避无法恢复；
- 外部参照项目同步迁移到新的稳定端点。

迁移时应保留现有明文端点作为可切换回退，并使用录制响应测试加密请求体和解析路径，不能让测试依赖实时网络。

### 5.2 QRC 头部元数据白名单（F8）

当前建议维持白名单。若以后拿到真实 payload 证明 `ly/mu/ma/pu` 等字段稳定且有用户价值，可以只扩展到 `LyricTextProcessor` 已支持的标准字段；不建议无条件保留所有 `[name:value]`，尤其是体积较大的 `[kana:]`。

### 5.3 罗马音歌词（F10）

接入罗马音不是单纯增加一个响应字段，还需要决定：

- 是否增加独立下载开关；
- 原文、翻译、罗马音三者的保存顺序；
- 内嵌歌词、外置 LRC 和仅翻译模式的行为；
- 三条时间轴不完全一致时的对齐与丢弃策略；
- QQ 请求中的 `roma` 是否默认开启及其额外限流成本。

这些问题应先形成产品方案，再实现 provider 和 UI。

### 5.4 两位时间戳（F11）

当前四舍五入与项目此前批准的精度改进一致，能够让 345 ms 输出 `.35`，并让 999 ms 正确进位到下一秒。改为截断会重新引入系统性负偏差，也会破坏现有测试，因此不修改。

### 5.5 decoder 共享重构（F12）

不建议当前抽取统一 decoder。可以共享的部分主要只有时间戳格式化，而该逻辑已经集中在 `LyricTextProcessor.FormatTimestamp`。只有在两套 decoder 再次出现相同缺陷或需要新增第三种逐词格式时，才值得重新评估更高层抽象。

## 6. 已知剩余风险

- 网易无歌词过滤依赖官方布尔标志；如果服务端只返回占位文本而不带标志，当前仍会保留该文本。应先收集真实响应，再决定是否维护严格的占位文案列表。
- QRC 行间元数据测试使用合成 payload；现有真实样本的元数据仍主要位于头部。
- provider characterization 使用录制或注入响应，不验证当天在线端点是否可达。
- QQ、网易均为非官方开放接口，服务端协议、风控和字段随时可能变化。
- 自动测试无法覆盖下载后的所有播放器兼容性；三位毫秒、翻译排列和元数据展示仍需代表性播放器抽查。

## 8. 后续建议顺序

1. 先在真实使用中观察网易无歌词响应和 QQ 行间元数据，不继续扩大规则。
2. 若出现未带布尔标志的网易占位文本，保存完整响应并基于样本讨论严格哨兵列表。

4. 罗马音功能另立设计任务，先确定 UI 与三语保存格式。
